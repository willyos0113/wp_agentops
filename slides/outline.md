# 簡報大綱

## 給 AI 的簡報製作說明

這份大綱會交給 AI 產生簡報，請依下列規則製作:

1. 頁面: 每個 `## pN | 標題` 是一頁投影片，標題照用，頁序不要調整，也不要自行增減頁面。
2. 括號標記: 內文中以 `(...)` 包起來的 Fig、screenshot 與其他說明，是給製作者的指示，不是簡報內容，不要把這些文字原樣放上投影片。
3. screenshot: 使用 `slides/` 資料夾中的圖片，檔名與編號對應(如 screenshot4 對應 `slides/screenshot4.png`)。請直接放原圖，不要重繪或自行生成；若找不到對應檔案，在該位置留一個標明編號的空框，並在完成後列出缺少的編號。
4. Fig: 直接畫在投影片上(用圖形、箭頭、圖表或表格)，不要去找圖片檔。括號內的說明是該圖要呈現的內容，圖中的節點名稱與數字請照說明使用。
5. 編號對應: p9、p10 的截圖標有「對應 ①」等字樣，請把截圖放在 Fig12 相同編號的節點旁，或在截圖上標出同樣的編號，讓聽眾能對照。
6. 數字與名詞: 大綱中的數字、計算過程、AWS 服務名稱與規格(如 t3.micro、db.t3.micro)請照用，不要改寫、四捨五入或補上大綱沒有的數據。
7. 文字量: 投影片上的文字以條列重點為主，可以精簡大綱的句子，但不要改變意思；以圖和截圖為主角，文字為輔。
8. 語言: 使用繁體中文，專有名詞維持英文原文。

## p4 | 想解決的問題

- 資料庫安全性: 平台涉及用戶隱私，資料庫安全性很重要。
- 維運人力不足: 公司規模小人力不足，需減輕人力維運負擔。
  (Fig2. 放兩個 icon，分別代表鎖頭、人力)

## p5 | 如何解決問題?

- 資料庫安全性: 採內外網段隔離，只有 Web 平台才可以連線資料庫，以提升資料庫安全性。
  (Fig3. 隔離示意圖: Internet → Web → DB)

- 維運人力不足: Web 平台日誌自動拋轉到監控平台，再利用監控平台 AI，自動調查 Web 日誌、AWS 資源操作紀錄等，提供根因分析報告給維運人員，減少人力手動排查成本。
  (Fig4. 監控流程示意圖: Web 日誌 → 監控平台 → AI 調查 → 報告 → 維運人員)

## p6 | 解決前後比較

- 資料庫安全:
  - 解決前: Web/DB 均可由外部存取，很危險。
  - 解決後: 只有 Web 才可存取 DB，避免 DB 暴露在外網。
    (Fig5. 左右並排的連線對比圖。左為解決前: Internet 有兩條箭頭，分別直接連到 Web 與 DB，連到 DB 的箭頭用紅色標示危險；右為解決後: Internet 只有一條箭頭連到 Web，再由 Web 連到 DB，Internet 直接連 DB 的路徑打叉，DB 外圍畫一個「內網」的框)

- 故障排查優化:
  - 解決前: 故障 → 1~2 分鐘告警信 → 登機器翻 log → 查 RDS 指標 → 查 AWS 操作紀錄 → 找到根因 → 手動恢復
  - 解決後: 故障 → 1~2 分鐘告警信 → AI 自動調查產出根因報告 → 手動恢復
    (Fig6. 上下兩條並排的流程對比圖，上為解決前、下為解決後。兩條流程的「故障 → 1~2 分鐘告警信」與「手動恢復」對齊，中間的排查步驟用不同顏色標示: 解決前是 4 個人工步驟，解決後是 1 個 AI 自動步驟，讓人工步驟的減少一眼可見。除了 1~2 分鐘以外不要標其他時間。實際畫面與證據留到 p9、p10 的故障演練)

## p7 | 架構方案評估

- EC2 規格: 選 t3.micro，決定規格的是記憶體，不是 CPU。
  - CPU: 尖峰需求 0.002 vCPU，t3.micro 穩定提供 0.2 vCPU，只用到 1%。
    (Fig7. CPU 需求 vs t3.micro 供給的長條（0.002 vs 0.2 vCPU），標出「只用到 1%」)
    (口頭說明用，不放上投影片: 每日 50 人次 × 每次看 5 頁 = 每日 250 頁；尖峰一小時佔全日 15% 約 38 頁，約每秒 0.01 頁；WordPress 產生一頁約 0.2 秒 CPU，等於 0.002 vCPU)
  - 記憶體: 需求 760MB，t3.nano(0.5GiB) 不夠，t3.micro(1GiB) 才夠。
    (Fig8. 記憶體堆疊條：400MB 固定 + 360MB 程序 = 760MB，畫上 0.5GiB 與 1GiB 兩條線)
    (口頭說明用，不放上投影片: 作業系統、Apache 程序和 CloudWatch Agent 的固定開銷預估約 400MB；瀏覽器載入一頁最多同時開 6 條連線，每個程序假設 60MB，6 × 60MB = 360MB)

- 資料庫: 選 RDS 託管，每月多付約 12USD，換掉備份、修補、還原的維運人力。
  - RDS 託管 MySQL(db.t3.micro，20G): 每月 21.74USD，備份、修補、還原由 AWS 處理。
  - EC2 自建 MySQL(t3.micro): 每月 9.93USD，備份、修補、還原要自己處理。
    (Fig9. 自建 vs RDS 比較表：月費、備份、修補、還原、所需人力)
    (screenshot2: AWS Pricing Calculator 試算結果，縮小放在比較表旁作為價格出處)
