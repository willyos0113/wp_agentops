# 簡報大綱

## 給 AI 的簡報製作說明

這份大綱會交給 AI 產生簡報，請依下列規則製作:

1. 頁面: 每個 `## pN | 標題` 是一頁投影片，標題照用，頁序不要調整，也不要自行增減頁面。
2. 括號標記: 內文中以 `(...)` 包起來的 Fig、screenshot 與其他說明，是給製作者的指示，不是簡報內容，不要把這些文字原樣放上投影片。
3. screenshot: 使用 `slides/` 資料夾中的圖片，檔名與編號對應(如 screenshot4 對應 `slides/screenshot4.png`)。請直接放原圖，不要重繪或自行生成；若找不到對應檔案，在該位置留一個標明編號的空框，並在完成後列出缺少的編號。
4. Fig: 直接畫在投影片上(用圖形、箭頭、圖表或表格)，不要去找圖片檔。括號內的說明是該圖要呈現的內容，圖中的節點名稱與數字請照說明使用。
5. 編號對應: p7、p8 的截圖標有「對應 ①」等字樣，請把截圖放在 Fig11 相同編號的節點旁，或在截圖上標出同樣的編號，讓聽眾能對照。
6. 數字與名詞: 大綱中的數字、計算過程、AWS 服務名稱與規格(如 t3.micro、db.t3.micro)請照用，不要改寫、四捨五入或補上大綱沒有的數據。
7. 文字量: 投影片上的文字以條列重點為主，可以精簡大綱的句子，但不要改變意思；以圖和截圖為主角，文字為輔。
8. 語言: 使用繁體中文，專有名詞維持英文原文。

## p1 | 業務情境與達成目標

- 公司主要業務為販賣台灣手搖飲料給日本，利用 WordPress 為公司規劃一個網路通路平台:
  - 用戶規模估算: 以 2025 年訪台日本旅客 150 萬人次中，約有 0.3% 成為本平台用戶，每人一年上平台約 4 次，平均每日約 50 人次。
    (Fig1. 用戶規模漏斗示意圖: 150 萬人次 → 0.3% → 4,500 人 → ×4 次/年 → 每日約 50 人次)
  - 核心目標: 確保平台資料庫安全，自動化維運減少人力負擔。

- 以 Web/DB 分離加上 CloudWatch 自動調查，達成資料庫不對外、系統故障自動產出根因報告。

## p2 | 想解決的問題

- 資料庫安全性: 平台涉及用戶隱私，資料庫安全性很重要。
- 維運人力不足: 公司規模小人力不足，需減輕人力維運負擔。
  (Fig2. 放兩個 icon，分別代表鎖頭、人力)

## p3 | 如何解決問題?

- 資料庫安全性: 採內外網段隔離，只有 Web 平台才可以連線資料庫，以提升資料庫安全性。
  (Fig3. 隔離示意圖: Internet → Web → DB)

- 維運人力不足: Web 平台日誌自動拋轉到監控平台，再利用監控平台 AI，自動調查 Web 日誌、AWS 資源操作紀錄等，提供根因分析報告給維運人員，減少人力手動排查成本。
  (Fig4. 監控流程示意圖: Web 日誌 → 監控平台 → AI 調查 → 報告 → 維運人員)

## p4 | 解決前後比較

- 解決前:
  - 資料庫: Web/DB 同一台，且均可對外連線
  - 故障發生時: 等用戶回報
  - 故障排查: 人工登機器翻 log、AWS web console 設定

- 解決後:
  - 資料庫: DB 獨立於內網，只有 Web 主機才能連線
  - 故障發生時: 1~2 分鐘內出現 5xx 告警信，10 分鐘後自動產出分析報告
  - 故障排查: AI 自動調查 Web 日誌、RDS 指標、CloudTrail 變更紀錄

## p5 | 架構方案評估

- EC2 規格的選擇
  - CPU 算「每秒要多少運算量」
    - 每次造訪假設看 5 頁，50 × 5 = 每日 250 頁。
    - 假設尖峰一小時佔全日 15%，每小時處理頁數: 250 × 15% ~ 38頁。
    - 換算每秒處理頁數: 38 ÷ 3,600 秒 ~ 每秒 0.01 頁。
    - 另假設 WordPress 產生一頁約要 0.2 秒 CPU，每秒 0.002 秒的運算，也就是 0.002 顆 vCPU。
    - 以 t3.micro 規格穩定提供 0.2 顆來看，需求只佔 1%，運算量一定足夠！
      (Fig6. CPU 需求 vs t3.micro 供給的長條（0.002 vs 0.2 vCPU）)

  - MEM 算「同時要多少記憶體」
    - 作業系統、Apache 程序和 CloudWatch Agent 佔約 400 MB 的固定開銷(假設預估)。
    - 尖峰時約每 100 秒處理一頁，即使只有 1 位訪客，瀏覽器載入一頁也會同時開最多 6 條連線，假設每個程序佔 60MB，則 6 × 60MB = 360MB
    - 以上，合計需 400 + 360 = 760MB
      (Fig7. 記憶體堆疊條：400MB 固定 + 360MB 程序 = 760MB，畫上 0.5GiB 與 1GiB 兩條線)

  - 評估結果: t3.nano(0.5GiB) 不夠，至少需 t3.micro(1GiB) 才夠用。

- DB 自建 vs RDS 託管的選擇
  - 用 RDS 託管 MySQL，採 db.t3.micro 容量 20G，每月計約 21.74USD。
  - 用 EC2 自建 MySQL，採 t3.micro 試算每個月 9.93USD，但自動備份、修補和還原等資料庫與作業系統的維運就需要額外人力處理。
    (screenshot2: AWS Pricing Calculator 試算結果)
    (Fig8. 自建 vs RDS 比較表：月費、備份、修補、還原、所需人力)

  - 評估結果: 採 RDS 託管方案，每月多付約 12USD，但可省下自建 MySQL 後所需的維運人力。
